# 厦门在招岗位爬取与匹配筛选系统

> 从厦门大学就业信息网爬取招聘岗位，按用户设定的条件筛选出与专业对口的岗位，导出为可直接投递的清单。

## ⚠️ 2026-09-20 抓取策略重大变更（务必先读）

**本项目最初的爬虫犯了方向性错误，已修复。**

原方案：以「种子职位 ID」为中心做 ±N 双向枚举（`--scan-range`），
并在代码注释与文档中写下结论「该站点不支持关键词检索」。

**这个结论是错的。** 厦大就业网自带一个公开的多维筛选检索页：

```
GET https://jy.xmu.edu.cn/job/search
```

无需登录，支持 **13 个筛选维度**（地区 / 学历 / 工作性质 / 最低薪资 /
发布时间 / 单位性质 / 单位规模 / 需求专业 / 行业 / 职能 …），
每页 20 条，分页为 PATH 风格 `/page/N`。

枚举 ID 的真实代价：

| | 旧方案（ID 枚举） | 新方案（检索接口） |
|---|---|---|
| 请求次数 | 61 次（`--scan-range 30`） | 16 次（厦门+本科全量） |
| 拿到岗位 | 约 11 条 | 288 条（厦门+本科+全职） |
| 城市可控 | ❌ 完全随机 | ✅ 精确指定 |
| 条件可控 | ❌ 无法表达学历/性质/专业 | ✅ 13 个维度 |
| 覆盖度 | ❌ 只覆盖一个 ID 区间 | ✅ 该条件下全量 |

现改为**两段式抓取**：

```
第 1 段  检索页按条件遍历列表（含 jid/公司/岗位/薪资/城市/性质/学历）
第 2 段  对每个 jid 抓详情页，补「需求专业」（列表页没有这个字段）
第 3 段  本地关键词加权打分（站点算不出综合匹配度，这部分保留）
```

- 实现见 `spiders/xmu_career.py`（文件头部有完整探测记录与站点事实）
- 列表数据是**两层 base64+zlib 压缩内嵌**在页面里的，解码见 `core/decoder.py`
- 检索条件用 `--search-city / --search-education / --search-major …` 表达，
  `--scan-range` 已移除

## 项目背景

秋招期间，一名求职者需要从数百个岗位中筛选出与自己专业对口的岗位。人工逐条翻阅就业网存在三个问题：

1. **效率低**——单个平台翻 100 个岗位约需 30 分钟
2. **易遗漏**——岗位按公告分散发布，无法一次看全
3. **判断主观**——「这个岗位到底算不算对口」缺乏统一标准

本项目把这三件事自动化：**爬取 → 条件筛选 → 量化打分 → 排序导出**。

## 技术栈

| 层次 | 技术 |
|---|---|
| 爬取 | `requests` + `BeautifulSoup` + `lxml`，站点检索接口 `/job/search` |
| 数据获取 | 两层 base64+zlib 内嵌数据的解码（`core/decoder.py`） |
| 存储 | `SQLite`（唯一索引实现去重） |
| 数据处理 | `pandas` |
| 打分 | 自研规则引擎（双通道：岗位方向 + 专业准入，含专指度衰减） |
| 条件筛选 | `JobFilter` 条件对象（可 CLI 传参 / 可存 JSON 复用） |
| 导出 | `openpyxl`（带条件着色） |
| 测试 | `pytest`（116 个测试用例） |

这是本项目「筛选」能力的入口。所有条件都是可选的，不填即不限制。

| `--min-score` | 最低匹配分 | `--min-score 16` |

## 核心设计说明

### 一、匹配度打分引擎（`core/matcher.py`）★核心

这是项目的核心。把「岗位是否适合本专业」这件事量化成可复现的分数。

#### 打分模型（v2，2026-09-20 重构）

```
总分 = 岗位方向分（只看岗位名称） + 专业准入分（只看专业要求） - 反向词扣分
```

两个通道**语义独立**，这是 v2 相对 v1 的根本改动：

| 通道 | 看什么 | 回答什么 | 怎么算 |
|---|---|---|---|
| 岗位方向分 | 岗位名称 | 这个岗位是什么方向 | 取命中词的**最高权重**（不累加） |
| 专业准入分 | 需求专业 | 我的专业能不能过门槛 | 加权和 + 几何衰减 + 专指度系数，封顶 15 |

**为什么必须拆开**（这是 v1 实测踩出来的坑）：

v1 用一张词表对「岗位名称 + 专业要求」整体加权求和，结果出现两件荒谬的事：

1. **分数与「专业罗列数量」正相关**。「客户服务岗」的专业要求列了 48 个专业，
   命中 9 个关键词 → 累加到 53 分；而「数据分析/软件开发管培生」只有 35 分。
   但一家公司把专业写 40 个，恰恰说明它对专业**没有偏好**——对求职者是弱信号。
   线性累加把「无偏好」当成了「多处命中」，结论完全反了。
2. **「不限专业」得 0 分**。中行信息科技岗、浩鲸云计算开发工程师、睿云联
   C++后台/Web前端/运维/测试等 8 个技术岗因为专业要求写「不限专业」，
   一个关键词都命中不了，被打 0 分直接扔掉。
   这是把「无门槛」编码成了「不匹配」——中性值被当成了负值。

拆开之后，「方向不对」的岗位无论专业写多少，方向分都是 0；而「不限专业」
走独立分支拿基准分，技术岗不再被误杀。

#### 三个辅助机制

| 机制 | 规则 | 解决的问题 |
|---|---|---|
| 专指度衰减 | 第 i 个命中词贡献 = 权重 × 0.7^(i-1)；命中数 > 4 时再乘 4/n | 抵消「列得多就分高」 |
| 专业通道封顶 | 15 分（= B 级上界） | 单靠专业最多到 B 级，进 A/S 必须有方向分配合。否则「财务岗」因为在专业里点名了信息与计算科学，分数会超过算法工程师（实测发生过） |
| 缺失字段标记 | 专业字段为空 → `【专业字段缺失】`，不当成不匹配 | 数据缺失 ≠ 真实值为 0（同「调试记录 · 问题五」的静默失败类型） |

「不限专业」基准分 = 6（C 级上段）：
- 纯「不限专业」+ 无关岗位（行政、教师）→ 6 分，不干扰重点清单
- 「不限专业」+ 技术方向（开发 6 / 运维 6 / 后台 8）→ 11~14 分进 B 级，能被筛到

#### 关键词权重（见 `config.py`）

| 关键词 | 权重 | 设计依据 |
|---|---|---|
| 信息与计算科学 | 10 | 直接点名专业，最高优先 |
| 数学类 / 统计学类 / 数理统计 / 应用数学 | 8 | 专业所属门类，招聘系统常用表述 |
| 数据科学 / 数据分析 / 算法工程 | 7 | 专业能力可迁移的核心方向 |
| 金融科技 / 量化 | 6 | 结合统计背景的交叉方向 |
| 计算机类 / 软件工程 | 5 | 课程有覆盖，但竞争更激烈 |

岗位方向词表（`config.DIRECTION_WEIGHTS`）单独维护，数据类岗位权重最高
（数据仓库/数据开发/数据分析 = 12），其次是算法/AI 类（10），再次是工程类（6）。

另有一个**子串去重**：公告里写「计算机科学与技术」时，词表里的「计算机」
也会命中，白送一次权重。因此短词若被长词覆盖则不重复计权。

**等级映射**：S(≥25) / A(≥16) / B(≥8) / C(≥0)

#### 为什么用规则引擎而不是机器学习模型？

- **可解释**：能明确说清"这个岗位为什么 24 分"，这是求职决策场景的刚需
- **零标注**：284 条数据训练不出监督模型，规则引擎可立即冷启动
- **可迭代**：权重表是纯配置。本次 v2 重构就是「用真实数据发现偏差 → 改规则
  → `--rescore` 秒级重算 → 用新分布验证」的闭环，不需要重新标注训练

**改了权重怎么生效**：`python main.py --rescore`（不联网，秒级）。
存储层用 `INSERT OR IGNORE` 去重，重复记录会跳过——所以直接重跑**不会**更新
已有记录的分数，必须走 `--rescore`（或清库重抓，代价大得多）。

### 二、用户条件筛选（`core/filters.py`）★

把「用户想看什么样的岗位」抽象成一个条件对象 `JobFilter`，支持 9 类条件自由组合（AND 关系）。

**职责边界**——两个模块各管一件事，避免同一条规则两处实现：

```
core/matcher.py  打分：这个岗位对口不对口   （客观，与用户偏好无关）
core/filters.py  筛选：这个岗位我要不要看   （主观，取决于用户条件）
```

**三个设计决策：**

1. **筛选条件是一个对象，不是一组散落的参数。**
   因此它可以被单元测试（20+ 用例覆盖）、被序列化成 JSON 反复复用（`--save-filter` / `--filter-file`）。

2. **入库订单是全集，导出订单是筛选集。**
   所以调条件不必重新爬取 —— 爬一次 2.5 分钟，重筛是毫秒级。

3. **排序规则：目标城市优先 → 匹配分降序。**
   原来「城市优先」的排序写在流水线里，紧接着就被 `score_jobs()` 按分数重排覆盖掉了，
   等于从未生效（详见「调试记录 · 问题六」）。现在统一在 `apply()` 里一次算完。

**几个刻意的宽松处理**（宁可多给一条，不要误杀）：

| 情况 | 处理 | 理由 |
|---|---|---|
| 薪资标注为「面议」或为空 | **保留** | 信息缺失 ≠ 不满足条件 |
| 学历字段为空 | **保留** | 同上 |
| 非目标城市 | 默认**保留**（除非显式给了 `--city`） | 厦大就业网是全国性平台，数据不必过早丢弃 |

**关于为什么在内存里筛而不是写进 SQL：**
当前数据量在 10³ 量级，全量取回再筛选是毫秒级。换来的是条件组合可以被单独测试、被序列化。
若数据量涨到 10⁵ 以上，应把 `city` / `match_score` / `match_level` 这些能走索引的条件下推到 SQL，
只把薪资解析这类需要正则的条件留在内存。

### 三、数据去重（`core/storage.py`）

用 `(company, title)` 建唯一索引，配合 `INSERT OR IGNORE`，实现数据库层面的天然去重：

```sql
UNIQUE(company, title)
```

多轮抓取时重复岗位会自动跳过，返回新增条数便于统计。

### 四、文明爬虫约定（`core/fetcher.py`）

- **限速**：相邻请求间隔 ≥ `REQUEST_DELAY_SECONDS`（默认 1.5s）
- **重试**：指数退避（1s → 2s → 4s），最多 3 次
- **UA 轮换**：降低被误判为恶意流量
- **异常隔离**：单页解析失败不影响整体流程

## 打分模型迭代记录（v1 → v2，2026-09-20）

这段记录的是「用真实数据发现模型偏差 → 改规则 → 秒级重算 → 用新分布验证」
的完整闭环。它比"一次写对"更能说明工程判断力。

### 发现过程

抓取策略修好后，库里第一次有了 284 条完整数据（此前 ID 枚举只有 21 条杂数据）。
在完整数据上跑 v1 打分，排序明显不对：

| 岗位 | 专业罗列数 | v1 得分 | 说明 |
|---|---|---|---|
| 客户服务岗 @中远海运 | 48 | **53** | 罗列最多，分数最高 |
| 供应链管理岗 @中远海运 | 40 | **53** | 同上 |
| 人力专员 @中远海运 | 17 | 20 | |
| 数据分析/软件开发管培生 @活石网络 | 20 | 35 | 明显更对口，却更低 |
| 算法工程师 @微著智能装备 | 8 | 26 | 罗列最少，分数最低 |

同时另一头也出问题：中行信息科技岗、浩鲸云计算开发工程师、睿云联
C++后台/Web前端/运维/测试等 **8 个技术岗全部 0 分**。

### 三个根因

1. **把「无门槛」编码成了「不匹配」**。`score()` 只对命中的关键词加分，
   「不限专业」一个词都命中不了 → 0 分。但它的真实语义是"人人可投"，
   是中性值，不是负值。
2. **加权求和无归一化**。一家公司把专业写 40 个，恰恰说明它对专业**没有偏好**
   ——对求职者是弱信号。但线性累加把"命中 9 个词"当成了 9 次加分，
   于是"无偏好"的岗位反而吃香，结论完全反了。
3. **数据缺失被当成真实值**。14 条（4.9%）岗位的详情页没解析出专业字段，
   v1 让它们静默落在 0 分档，与"真实不匹配"混在一起无法区分。

### 修复

| 缺陷 | 修复 | 验证 |
|---|---|---|
| 不限专业 = 0 分 | 走独立分支给基准分（6 分）；技术方向可叠加方向分 | 6 个被误杀的技术岗全部回到 B 级（10~14 分） |
| 罗列型虚高 | 打分拆双通道 + 专指度衰减（几何衰减 × 4/n）+ 专业通道封顶 | 客服岗 53→11、供应链 53→11；数据分析管培生 35→27 升到第一 |
| 缺失静默 | 显式标记 `【专业字段缺失】`，与"真实不匹配"区分 | 新测试断言两条路径的可解释输出不同 |

### 一个调参时踩的坑（值得记下）

第一次把专业通道封顶设为 20，结果「财务岗」因为在专业里点名了
「信息与计算科学、应用数学、数学类」，拿满封顶 20 分排进 A 级，
比算法工程师（20 分）并列。

**根因**：封顶值高于 A 级门槛（16）时，单靠专业字段就能撑进 A 级。
专业要求只代表"能不能过门槛"，不代表"岗位对口"。

**修正**：封顶降到 15（= B 级上界），让「进 A/S 必须有方向分配合」成为硬约束。
财务岗随之落到 15 分 B 级。

### 新测试

`tests/test_matcher_v2.py`（18 个用例）把三个偏差固化成断言，
以后调权重若把它们改回去，测试会直接失败。

**改了权重表怎么生效**：`python main.py --rescore`（不联网，秒级）。
不能直接重跑——存储层 `INSERT OR IGNORE` 会跳过已有记录，分数不会更新。


## 调试记录（可写入简历 / 面试可讲）

开发过程中通过单元测试与真实站点联调，暴露了八个真实问题，记录如下（按发现顺序）：

> 说明：以下问题四、问题五中提到的 `JobBoardSpider`、`DemoSpider` 等已在本轮
> 代码审查中作为**无用代码删除**（原因见「代码审查记录」一节）。此处保留原始
> 排查过程，因为它是真实的问题演进历史，面试时比"从没写错过"更有说服力。

**问题一：关键词表覆盖不全导致岗位被系统性低估**

测试用例 `test_statistics_major_match` 断言"数理统计类岗位应达 A 级"，实际只得 14 分（差 2 分）。

排查发现：招聘公告中"计算机"与"计算机类"两种写法都极常见，而关键词表只收录了后者。建行厦门分行的公告原文是"重点招收**计算机**、人工智能、数理统计及其他理工类专业"——因缺少"计算机"这一条目，该岗位漏加 5 分，被错误降级。

修复：补充"计算机""理工类专业"等高频表述，并在配置文件中注明原因。修复后该岗位正确升至 S 级（28 分）。

**问题二：路径层级写错导致文件落盘位置错误**

首次运行时导出文件出现在项目外的 `outputs/output/` 目录。排查发现 `config.py` 位于项目根目录，`Path(__file__).parent.parent` 多向上取了一层。改为 `.parent` 后修复。

**问题三：误判页面元信息排版，导致城市与学历解析为空**

接入厦门大学就业信息网后，抓取到的岗位 **城市和学历字段全部为空**（`地点： | 薪资：7000-10000 | 学历：`）。

排查过程分两步走：

1. **第一层误判** —— 以为元信息是"一行用 `|` 拼接"（`"7000-10000 | 福建省厦门市思明区 | 全职 | 本科"`），于是写了 `line.split("|")`。实际 dump 文本行后发现，**`|` 是独立的一行**，没有任何一行同时包含 `|` 与其他内容，所以 `split` 分支永远不会触发。
2. **第二层误判** —— 通用字段提取函数 `_field("地点")` 假定是"键：值"形式。实测发现该站点**键与值也是分行的**（`'职能类别：'` 与 `'游戏策划专员'` 是两行），因此所有 `^键[:：](.+)$` 的写法全部失配。

修复：放弃"逐行找关键词"，改为 **锚点定位法** —— 以薪资行为锚点，向后顺序读取非 `|` 行，按 `[城市, 性质, 学历]` 的相对位置解析，并用白名单（`全职/兼职/实习` 等）与正则（学历枚举）逐项校验。修复后城市、学历、薪资、公司名全部正确解析。

> **可复用的方法论**：解析陌生页面时，**不要凭想象推断结构，先把 `soup.get_text("\n")` 逐行 dump 出来看**。"锚点 + 相对位置 + 白名单"比"逐行关键词匹配"稳健得多，因为前者只依赖字段顺序（网站改版极少调整顺序），后者依赖每一行的内部排版（改版必崩）。

**问题四：`--live` 挂了空壳爬虫 + 硬过滤导致全国数据被清空**

两个问题一起暴露，都是"连通性测试缺失"造成的。

**症状 A**：执行 `main.py --live` 后输出「抓到 0 条 / 未抓到任何数据，流程结束」，但单独运行 `spiders/xmu_career.py` 却能抓到 7 个职位。

**根因**：`main.py` 的 `run_pipeline()` 里，`--live` 分支实例化的是 **`JobBoardSpider`** —— 那是最早期写的**占位爬虫**，`SELECTORS` 全是模拟结构，真实站点上一个都匹配不到。我写好 `XmuCareerSpider` 后忘了把主流程接过去。这类"新模块写好了但没接线"的缺陷，单元测试抓不到（测试只覆盖 core 层），只有端到端跑才暴露。

**症状 B**（修好 A 之后浮现）：厦大就业网是**全国性平台**，抓到的岗位里有湖南、上海等地。原 `filter_by_city()` 是**硬过滤**（`return [j for j in jobs if city in j.city]`），非厦门岗位全被静默丢弃 —— 数据白抓了。

**修复**：

1. `main.py` 改为实例化 `XmuCareerSpider`，并抽出 `LIVE_SCAN_RANGE` 常量便于调参
2. 新增 `city_rank()` + `sort_by_city()` **软过滤**：目标城市(0) → 同省(1) → 其他(2)，**只排序、不丢数据**
3. 主流程改为：先看硬过滤结果，若目标城市有岗位则软排序全量；若为 0 则降级为「同省优先」并打印提示
4. 补 2 个回归测试锁定「软过滤不丢数据」这一契约

修复后 `--live` 实测：扫 11 个 ID 抓到 7 个真实职位，厦门 5 条，Top1 点触科技数值策划 77 分。

> 面试提示：问题四体现的是**端到端测试的必要性**。单元测试 17 个全绿，但 `--live` 依然是坏的 —— 因为单元测试只覆盖了 core 层的纯函数，没覆盖"主流程是否正确接线"。这正好说明测试金字塔里集成测试不可替代。

**问题五：导出的 Excel 只有表头、数据行全空（静默失败）**

**症状**：双击打开的 xlsx 表格，能看到中文表头，但下面 44 行全是空白。

**根因**：`storage.query_jobs()` 返回的字典 **key 是英文**（`company` / `title` / `match_level` …），而 `config.OUTPUT_COLUMNS` 定义的是**中文表头**（`公司` / `岗位` / `匹配等级` …）。导出器里 `df = pd.DataFrame(jobs)` 拿到的是英文字段，接着执行：

```python
for col in OUTPUT_COLUMNS:          # 全是中文名
    if col not in df.columns:       # 中文名当然都不在
        df[col] = ""                # ← 每一列都被填成空字符串
df = df[OUTPUT_COLUMNS]
```

结果 DataFrame 变成 14 列全是 `""`，`to_excel` 老老实实写出 44 行空数据。**全程不报任何错。**

原来是有一行 `df.rename(columns=header_map)` 想补救，但 `header_map` 写成了恒等映射（`{"公司": "公司", ...}`）—— 这是"想转换但忘了转换"的典型痕迹。

**修复**：

1. 在 `exporter.py` 里新增 `FIELD_TO_HEADER` 映射表（`company → 公司`、`title → 岗位`…），导出前先做真实重命名
2. 加**两道防线**防止再次静默失败：
   - 如果映射表一个 key 都没匹配上 → 直接抛 `ValueError("字段名无法识别")`
   - 如果所有数据列都是空 → 抛 `ValueError("疑似字段映射错位，已中止导出")`
3. 补 4 个导出层回归测试，其中 `test_export_writes_actual_data` 逐列断言「不能整列为空」

**修复后实测**：44 行岗位全部正确写入，14 列中 12 列 100% 填充（「命中关键词」15/44 属正常 —— C 级岗位本就无关键词命中）。

> 面试提示：问题五是最有价值的一个 —— 它演示了**静默失败**的危险性。程序不报错、单元测试全绿、文件也有 7KB（因为写了 44 行空行），但结果完全不可用。这类缺陷的根因是**两处契约不一致**（取数用英文 key，表头用中文名），而 pydantic / dataclass 这类结构约束在这里帮不上忙。我的修法是"对齐契约 + 加显式失败断言"，让下一次错位能立刻炸出来，而不是又导出一个空表。

**问题六：城市优先排序算了但被丢弃，从未生效**

**症状**：想实现「厦门岗位排最前、其他城市靠后保留」，写了 `city_rank()` + `sort_by_city()`
并加了单元测试（还全绿），但实际输出里厦门岗位并不一定排在前面。

**根因**：流水线的执行顺序是

```python
city_jobs  = matcher.sort_by_city(raw_jobs, TARGET_CITY)   # ① 按城市排一遍 ← 白排
edu_jobs   = matcher.filter_by_education(city_jobs)
scored     = matcher.score_jobs(edu_jobs)                  # ② 内部 sorted(by score) ← 覆盖了①
storage.save_jobs(scored)                                  # ③ 写库时就按分数存的
...
all_jobs   = storage.query_jobs()                          # ④ SQL 又是 ORDER BY match_score
```

第 ① 步的排序结果在第 ② 步被按分数重排**完全覆盖**，第 ④ 步又从 SQL 里重新按分数取。
也就是说这段排序代码从头到尾没影响过任何输出 —— 它只是一个昂贵的空操作。

**为什么测试没发现**：`sort_by_city()` 自身的行为是对的（输入 3 条输出 3 条、顺序也正确），
单元测试断言的是「这个函数干得对不对」，而不是「这个函数的结果有没有被用上」。
**单元测试测不出「算了但没人用」这类问题**，这是它天生的盲区。

**修复**：把筛选和排序合并到同一个地方 —— `JobFilter.apply()`

```python
kept.sort(key=lambda r: (
    self.city_priority(r["city"], target),   # 先按城市优先级
    -r["match_score"],                        # 再按分数
))
```

排序只在最终输出前算一次，中间没有第二个环节能覆盖它。
并补了回归测试 `test_sort_puts_target_city_first`（构造「长沙 90 分 vs 厦门 10 分」，断言厦门必须在前）。

> 面试提示：问题六是八个问题里**最反直觉**的一个。代码本身没错、测试还全绿，
> 错的是「这段代码在流水线里的位置」。它说明一件事：
> **被测过的函数不等于被使用的函数**，链路级的验证不能靠单元测试替代。
> 这也解释了为什么后来我把筛选和排序合并进一个模块 —— 职责重叠的地方最容易出现这种"算了没人用"。

**问题八：`.bat` 按 Unix 文本格式生成，Windows 下整份脚本被拆碎**

**症状**：执行

```bat
run.bat --skip-crawl --city 厦门 --min-score 16 --level S,A
```

脚本没有运行，而是刷出一屏莫名其妙的报错：

```
'en' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'分桶蛊例级===' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'.st_core.py' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'se' 不是内部或外部命令，也不是可运行的程序或批处理文件。
```

**根因**：文件是用 **UTF-8 编码 + LF 换行**生成的，而 cmd.exe 在中文 Windows 下：

| 环节 | 问题 |
|---|---|
| 编码 | 按 **GBK(936)** 解码 UTF-8 文件 → 中文注释与提示全成乱码 |
| 乱码内容 | 乱码字节里恰好含 cmd 特殊字符（`\|` `&` `>`）→ 命令行被从中间拆断 |
| 换行 | `LF` 不是 Windows 原生换行 → `if (...)` 这类多行块解析失效 |

三者叠加的结果就是：**每一行都被当成一条独立命令去执行**，于是满屏「不是内部或外部命令」。
注意看 `.st_core.py` 那一行 —— 它原本是 `"%VENV_PY%" -m pytest tests\test_core.py -v`，
被乱码拆得只剩尾巴。

**修复**：把两个 bat 重新生成为 **GBK + CRLF + 无 BOM**：

```python
text = content.replace("\r\n", "\n").replace("\n", "\r\n")   # 统一转 CRLF
path.write_bytes(text.encode("gbk"))                          # GBK 编码落盘
```

落盘后立刻验字节，而不是凭感觉：

```
written: run.bat
  bytes   = 1834
  first16 = 40 65 63 68 6F 20 6F 66 66 0D 0A 73 65 74 6C 6F
            └──────── "@echo off" ────────┘ └CRLF┘ └"set"...
  crlf    = 67
  bom     = False
```

`0D 0A` 就是 CRLF 的确认信号；`bom = False` 确保文件开头没有 BOM 污染第一行命令。

同时**去掉了原先的 `chcp 65001`** —— GBK 文件切到 65001 会让中文提示两侧编码不一致，
反而更乱。改为 `set PYTHONIOENCODING=gbk:replace`：Python 输出的中文在 936 控制台下正常，
且万一遇到 GBK 表示不了的字符也只是显示成 `?`，不会让程序崩掉。

**顺带修正了工作方法**：上一轮我改了 `main.py`，却**只测了「venv 直调」这条路径，没测 bat 本身**。
而用户实际使用的入口是 bat，不是 `python` 命令 ——
**测试必须覆盖用户真正会走的路径，而不是最方便测试的路径。**

> 面试提示：问题八是八个问题里唯一的**平台格式**问题，与技术无关，
> 纯粹是「用 Unix 思维生成 Windows 脚本」。
> 排查要点是：看到满屏「不是内部或外部命令」要立刻反应过来 ——
> **这不是代码问题，而是文件根本没被正确解析**，跟 Python 一点关系都没有。
> 去查文件字节比查代码快得多：`ReadAllBytes` 看前 16 字节，有没有 `0D 0A` 一眼便知。

## 使用须知（补充）

**关于「只看厦门」**

厦大就业网是全国性平台，抓到的岗位遍布各省。默认（不加 `--city`）会保留全部数据、
只把厦门排在最前；想只看厦门，直接加参数即可：

```bash
python main.py --skip-crawl --city 厦门
```

**关于导出 Excel 的列**

「命中关键词」列对 C 级岗位是空的，这是**预期行为**（C 级意味着没有任何关键词命中）。
若发现**所有**数据列都空，说明字段映射错位，程序会直接抛错而不是给你一个空表。

**关于筛选结果为 0 条**

程序会提示可放宽的方向，并跳过导出（不会给你一个空表）。先用
`python main.py --stats` 看看库里实际有哪些数据，再决定条件。

**关于导出文件名**

默认按「条件 + 时间戳」命名（如 `岗位清单_厦门_SA_min16_20260918_125752.xlsx`），
这样连着试几套条件时结果不会互相覆盖，看文件名就知道是哪套条件跑出来的。
想自己命名用 `--out`。

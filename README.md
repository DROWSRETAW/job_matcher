# 厦门在招岗位爬取与匹配筛选系统

> 把厦门大学就业信息网上「你能投、且值得投」的岗位筛出来，导成一份可以直接照着投的 Excel 清单。

**数据来源**：厦门大学就业信息网（https://jy.xmu.edu.cn）· 公开页面，无需登录

**当前版本**：`v1.4.0`（2026-09-24）· 本次新增 **DWD 清洗层与技能标签**，并给下架判定补上「检索口径必须一致」这条前提，详见文末[版本历史](#版本历史)

---

## 一、项目定位与核心功能

### 它解决什么问题

学校就业网上的在招岗位有几百条，但只能按单个条件筛选；你真正想知道的是「哪些岗位既在我的专业口径内、又是我该投的方向」——这个判断目前只能一条条翻。

本项目把这件事自动化：**按条件取数 → 逐条打匹配分 → 存进本地库 → 任意条件反复筛 → 导出 Excel**。

### 核心功能

| 功能 | 说明 |
|---|---|
| 多维条件检索 | 直接调用站点自带的筛选能力，按 城市 / 学历 / 工作性质 / 发布时间 / 最低薪资 / 需求专业 精确取数，而不是先把全国岗位抓回来再本地过滤 |
| 匹配度打分 | 每条岗位给出匹配分与 S/A/B/C 等级，并写明「为什么给这个分」——命中了哪些关键词 |
| 一次取数、反复筛选 | 岗位全量存进本地数据库，之后调整筛选条件是毫秒级、且不需要联网 |
| 条件可存可复用 | 检索条件和筛选条件都能存成方案文件，下次一条命令直接套用 |
| 成品 Excel | 14 列完整字段（含投递方式、截止时间、原文链接），按匹配等级着色、冻结首行 |

### 输出长什么样

导出的清单按「目标城市优先 → 匹配分从高到低」排序。当前库中的高匹配岗位示例：

| 等级 | 匹配分 | 公司 | 岗位 |
|---|---|---|---|
| S | 27 | 福建活石网络科技 | 数据分析/软件开发管培生 |
| A | 24 | 厦门微著智能装备 | CT重建算法工程师 |
| A | 20 | 厦门海景微电子 | AI开发工程师 |
| A | 19 | 厦门金美信消费金融 | 开发工程师 |

### 当前实测规模

- 全量口径（厦门 · 本科 · 全职 · 不限专业）**294 条**在招岗位
- 区域分布：思明 95 / 湖里 63 / 海沧 27 / 同安 19 / 翔安 18 / 集美 9（另有 63 条只到市级）
- DWD 清洗层：薪资解析 **100%**、学历归一 **100%**、经验填充 **100%**、技能标签平均 **2.21 个/岗位**（零标签岗位 0）
- 自动化测试 **332 个用例**，全部通过

## 二、数据是怎么存的：分层 + 可增量运行

> 一句话：**抓到的东西原样留档，加工的东西随时能重算。**

### 2.1 各层各管一件事

| 层 | 落在哪 | 存什么 | 职责 |
|---|---|---|---|
| **ODS** 贴源层 | `ods_job_snapshot` / `ods_crawl_batch` | 每次抓取的原始字段快照 | 如实记录，**只追加、不修改、不删除** |
| **DWD** 明细清洗层 | `dwd_job_detail` / `dwd_job_skill` | 清洗后的可聚合字段 + 技能标签 | 把「人读得懂、机器算不了」的文本拆成列 |
| 最新状态层 | `jobs` | 每个岗位一条最新记录 + 生命周期字段 | 回答「现在长什么样」，供筛选导出 |
| **ADS** 应用层 | `output/*.xlsx` | 按条件筛出的岗位清单 | 你实际要用的成品 |

**DWD 明细层**解决的是「原始文本没法算」这件事。站点把薪资写成 `7000-10000`、城市写成 `福建省厦门市思明区`，这些值能存、不能用 SQL 聚合，所以先拆成数值列：

| 拆什么 | 拆成 | 口径 |
|---|---|---|
| 薪资 | `salary_min` / `salary_max` / `salary_avg` | 统一折算成**月薪**，`salary_period` 记原始周期（月/年） |
| 城市 | `city_province` / `city_name` / `city_district` | 三级拆分，拆不出就留空，不猜 |
| 学历 | `education_level` | 归一成 不限/大专/本科/硕士/博士，多值**取最高** |
| 经验 | `experience_min` / `_max` / `_unlimited` | 「不限」与「应届」是两种语义，分开记 |
| 技能 | `dwd_job_skill` 明细表 | 从岗位名 / 需求专业 / 职能类别 / 语言要求抽词，别名归一 |

它是**纯派生层**：只读 ODS、只写自己的两张表，绝不回写 ODS。所以清洗规则改了直接重算，几秒钟完成，不必重抓：

```bash
python main.py --build-dwd    # 重算 DWD（不联网）
python main.py --dwd-stats    # 看填充率、薪资分布、技能热度榜
```

三条设计约定：**未知就是未知**（薪资解析失败记 0 条而不是 0 元）、**全量重建**（先清空再写入，幂等性天然成立）、**不臆造**（区县拆不出就留空，不填「市辖区」这种占位串）。

改造前只有 `jobs` 一张表，按「公司+岗位」去重后直接覆盖，由此有三个绕不开的问题：岗位改了薪资看不出来、下架了不知道、分不清哪些是新岗位。分层之后这三个问题一起解决。

最新状态层里每个岗位还带上了生命周期字段：

| 字段 | 含义 |
|---|---|
| `first_seen_at` | 第一次见到这个岗位的时间 |
| `last_seen_at` | 最近一次在列表里看到它的时间 |
| `change_count` | 抓取内容相对上次变过几次（改薪资、改专业要求） |
| `is_active` | 是否仍在招（按检索口径可判定时才更新） |
| `job_key` | 稳定主键，形如 `xmu:2400730` |

`job_key` 用的是站点的**职位 ID**，不是「公司+岗位名」——所以站点把岗位名从「27届校招-X」改成「X」不会再产生重复记录。

### 2.2 为什么能增量：详情页只抓「该抓的」

一次完整抓取的开销分布是这样的：

| 阶段 | 请求次数 | 耗时 |
|---|---|---|
| 列表页翻页 | 约 16 次 | 约 25 秒 |
| **详情页补「需求专业」** | **每条 1 次** | **约 7.6 分钟（占 94%）** |

时间几乎全花在详情页上，而这些内容两次抓取之间绝大多数根本不会变。所以：

- **列表页照常全量翻**——它是「有没有新岗位」的唯一来源，而且很便宜
- 详情页只抓这五种：**新出现的 / 列表信息有变的 / 从没抓到过专业的 / 快照由旧版解析器产生的 / 超过 7 天没刷新的**
- 其余跳过，专业与截止时间从历史快照回填——**跳过不等于丢字段**

第四种需要解释一下：解析器**学会新字段**时（比如本轮新增的工作经验、职能类别、语言要求），库里那些旧快照的列表指纹一模一样，靠「有没有变」永远判不出该重抓，新字段会一直是空的。靠「哪个字段为空就重抓」也不行——有些字段在站点上本来就可能为空，会陷入每轮都重抓、永远抓不完。所以显式记一个 `detail_schema_version`：版本低于当前的才排进重抓队列，抓完一轮就收敛。它天然支持分块续抓，`--detail-limit 100` 跑三轮即可补齐全库。

实测（厦门 · 本科 · 全职，20 条岗位）：

| 第几次跑 | 列表请求 | 详情请求 | 耗时 |
|---|---|---|---|
| 第 1 次（全新建库） | 1 | 20 | 约 40 秒 |
| 第 2 次（同一条件） | 1 | **0** | **约 1 秒** |

按全量口径（约 300 条岗位）算，第一次约 8 分钟，之后每次通常在 1 分钟以内。

### 2.3 分层之后新有的能力

```bash
python main.py --ods-stats           # 历次批次跑了什么、增量省下了多少请求
python main.py --ods-history 2400730 # 某个岗位的完整轨迹：薪资/专业是什么时候变的
python main.py --ods-changes 30      # 最近 30 天哪些岗位信息变了
python main.py --rebuild-state       # 从原始快照重建最新状态层（不联网，几秒钟）
python main.py --build-dwd           # 从原始快照重算清洗层与技能标签（不联网，几秒钟）
```

`--rebuild-state` 是「稳定数据源」最直接的体现：`jobs` 表坏了、误删了、改了字段口径，都能从 ODS 重新算出来，不必再花 8 分钟联网重抓。

**什么时候需要关掉增量**：怀疑数据没更新时，用 `--full-refresh` 强制全部重抓详情；想彻底重来则用 `--reset-ods` 连历史一起清掉。

## 三、主要使用场景

**1. 秋招找厦门的对口岗位（主线用法）**
默认口径就是为「数学类本科 · 2027 届 · 目标厦门」准备的：厦门 + 本科 + 全职 + 数学与统计类专业。跑一次就能拿到一批候选，重点看 S / A 级。

**2. 判断「机会盘子有多大」**
同一个市场按不同口径取数看差异：只按本专业精确匹配约 30 条，放宽到「不限专业」约 300 条。这个对比能帮你决定是该收窄方向还是扩大投递面。

**3. 盯新增岗位**
用发布时间条件只取近 3 天 / 近 1 周的岗位，每周跑一次，不用反复翻看老岗位。

**4. 换城市、换专业复用**
检索条件是参数化的，换成福州、泉州或换一个专业口径，同一条命令就能拿到另一批结果，适合横向对比异地机会。

**5. 快速排除噪音**
用排除词一次性滤掉销售、客服、市场推广这类明显不对口的岗位。

## 四、安装与快速上手

### 环境要求

- Windows（批处理入口为 Windows 原生脚本）
- Python 3.8 及以上
- 依赖库见 `requirements.txt`：requests / beautifulsoup4 / lxml / pandas / openpyxl

### 方式一：双击运行（最省事）

在项目目录下**双击 `一键运行.bat`**。它会自动找到可用的 Python 解释器、检查依赖（缺了就按 `requirements.txt` 自动安装），然后执行完整流程。

想带参数时，在项目目录开一个命令行窗口，用通用入口 `run.bat`：

```bat
run.bat --stats
run.bat --skip-crawl --city 厦门 --min-score 16 --level S,A
run.bat test          :: 跑一遍自动化测试，确认环境没问题
```

> `run.bat` 会自动按 `.\.venv` → `.\venv` → 环境变量 `%PYTHON%` → `PATH` 中的 `python` 依次寻找解释器。
> 如果 Python 装在别处，把 `local.bat.example` 复制成 `local.bat`，在里面填一行解释器路径即可（该文件不会进入版本库）。

### 方式二：命令行运行

```bash
# 建虚拟环境并安装依赖（只需一次）
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

# 运行
python main.py
```

### 怎么算「跑通了」

执行结束后，你会看到流水线逐步打印，并以类似下面的结果收尾：

```
[1/5] 检索岗位（使用站点自带的多维筛选） ...
      取到 284 条岗位（列表请求 16 次，详情请求 284 次）
      其中取到「需求专业」的 270 条

[2/5] 专业匹配度打分 ...
      等级分布：S(极高匹配)=1 | A(高度匹配)=13 | B(一定匹配)=38 | C(相关性较弱)=232

[3/5] 入库（按 公司+岗位 去重） ...
      新增 284 条，重复跳过 0 条

[4/5] 按条件筛选 ...
      命中 14 条 / 库中共 284 条

[5/5] 导出 Excel ...
      已导出：...\output\岗位清单_厦门_SA_min16_20260920_223512.xlsx
```

导出文件在 `output/` 目录下。**第一次跑想先确认环境正常、又不想等**，可以小规模试跑：

```bash
python main.py --max-pages 2 --detail-limit 10
```

## 五、典型用法示例

### 日常三招

```bash
# 1. 看库里现在有什么（不联网、不导出）
python main.py --stats

# 2. 只挑高匹配的，秒级出清单
python main.py --skip-crawl --min-score 16 --level S,A

# 3. 只看近一周新发的岗位
python main.py --search-time 近1周
```

### 取数口径（决定向站点要哪一批岗位）

| 命令 | 效果 |
|---|---|
| `python main.py` | 默认口径：厦门 + 本科 + 全职 + 数学/统计类专业，约 24 条候选 |
| `python main.py --search-major 不限` | 放开专业限制，取厦门全部本科全职岗位，约 294 条（**建库用的就是这个口径**） |
| `python main.py --search-city 福州` | 换成福州（支持厦门/福州/泉州/漳州等，填中文名） |
| `python main.py --search-time 近3天` | 只取近 3 天发布的 |
| `python main.py --search-salary-min 8000` | 只取月薪 8000 起的 |
| `python main.py --no-detail` | 不抓详情页，速度快很多，但缺「需求专业」，匹配分仅供参考 |
| `python main.py --max-pages 2 --detail-limit 10` | 快速试跑：只取 2 页列表、前 10 条详情 |

> 口径一旦定下来就别频繁改：增量判定与上架状态都以「同一批岗位」为前提。库里现有的 294 条是按 `--search-major 不限` 建的，想继续在同一批数据上增量，就带着这个参数跑。

### 看清洗后的数据（DWD 明细层）

```bash
# 填充率、薪资分布、城市薪资、技能热度 TOP15 一次看完
python main.py --dwd-stats
```

数据表 `dwd_job_detail` 一行一个岗位，字段都是可直接聚合的数值/枚举（`salary_min` / `city_district` / `education_level` / `experience_min`…），`dwd_job_skill` 一行一个「岗位 × 技能」。所以「厦门数据分析岗的月薪中位数」「要求 Python 的岗位有多少」这类问题，一句 SQL 就能答：

```sql
SELECT city_name, ROUND(AVG(salary_avg)) AS 平均月薪, COUNT(*) AS 岗位数
  FROM dwd_job_detail WHERE education_level = '本科' GROUP BY city_name;
```

### 筛选条件（决定导出清单里留哪些）

| 参数 | 效果 |
|---|---|
| `--city 厦门` / `--city 厦门,福州` | 限定城市，多个用逗号分隔 |
| `--min-score 16` | 最低匹配分（S≥25 / A≥16 / B≥8） |
| `--level S,A` | 只要指定等级 |
| `--keyword 数据` | 关键词，匹配公司名或岗位名 |
| `--major 数学` | 专业要求里必须含「数学」 |
| `--exclude 销售,客服` | 排除关键词 |
| `--top 20` | 最多输出 20 条 |
| `--out 我的清单.xlsx` | 指定导出文件名（默认按条件自动命名） |

### 数据维护

```bash
# 改了打分规则后重算全部分数（不联网，秒级）
python main.py --rescore

# 从 ODS 原始快照重建最新状态层（不联网，秒级）
python main.py --rebuild-state

# 从 ODS 重算 DWD 清洗层与技能标签（不联网，秒级，可反复重跑）
python main.py --build-dwd
python main.py --dwd-stats

# 只清最新的状态层：会自动从 ODS 重建，数据不丢
python main.py --reset-db

# 彻底重来：连 ODS 历史一起丢弃（不可恢复，谨慎）
python main.py --reset-ods --reset-db --city 厦门
```

> ⚠️ **换检索口径时注意**：程序会把「本批列表里没再出现的岗位」标成下架，但这条判断只在**本批与上一批问的是同一个问题**时成立。口径一变窄（比如从「不限专业」换成「数学类」），返回的岗位数自然变少，少掉的那些完全可能还在招。所以程序会拿本批口径去比上一批成功批次的记录，不一致就**只记录不判定**，并在日志里写明两侧口径。想在日志里看到明确原因，就留意这句：`本次不判定下架（本批检索口径与上一批不同 —— …）`。

### 把一套条件存下来反复用

```bash
# 检索方案
python main.py --search-city 厦门 --search-major 不限 --save-search xiamen-all.json
python main.py --search-file xiamen-all.json

# 筛选方案
python main.py --city 厦门 --min-score 16 --level S,A --save-filter focus.json
python main.py --skip-crawl --filter-file focus.json
```

命令行参数的优先级高于方案文件，临时想改某个条件，直接加在命令后面即可覆盖。

`python main.py -h` 可以查看全部参数。

## 六、配置说明

所有可调项集中在 `config.py`，改配置不需要动其他代码。

### 检索范围与排序

| 配置项 | 作用 | 默认值 |
|---|---|---|
| `TARGET_CITY` | 目标城市，决定排序时谁排最前 | `厦门` |
| `DEFAULT_MAJOR_KEYS` | 默认专业口径（可投的专业范围） | 信息与计算科学、数学类、统计学 |
| `MAJOR_CODES` | 专业名称 → 站点代码对照表 | 已含数学类、统计、计算机、软件工程等 |
| `CITY_CODES` | 城市名称 → 行政区划代码对照表 | 福建省各市 + 主要一二线城市 |
| `PROVINCE_CITIES` | 同省城市清单，用于「同省岗位优先排序」 | 福建、江苏 |

> 检索条件里的城市、学历、专业都填**中文名**，程序会自动翻译成站点需要的代码。

### 打分规则

分数 = **岗位方向分（看岗位名称）** + **专业准入分（看专业要求）** − 反向词扣分。

| 配置项 | 作用 |
|---|---|
| `DIRECTION_WEIGHTS` | 岗位方向词表：数据 / 算法 / 开发等方向各值多少分 |
| `KEYWORD_WEIGHTS` | 专业关键词表：专业要求里出现「信息与计算科学」「数学类」等各加多少分 |
| `NEGATIVE_KEYWORDS` | 反向词表：命中销售、客服等直接扣分 |
| `MATCH_LEVELS` | 等级阈值：S≥25 / A≥16 / B≥8 / C≥0 |

想调整「什么算对口」，改这几张表就够了；改完执行 `python main.py --rescore`，已有数据会用新规则重算。

### 输出与采集节奏

| 配置项 | 作用 | 默认值 |
|---|---|---|

## 七、常见问题

**Q：运行时报 `ModuleNotFoundError: No module named 'pandas'`**
说明当前用的是没装依赖的 Python。改用 `run.bat` 运行——它会自动挑选可用的解释器，缺依赖会自动安装。如果你自己建了虚拟环境，先激活再运行。

**Q：提示「未取到任何岗位」**
先检查检索条件拼写：城市、学历、工作性质都要用中文名（如「厦门」「本科」「全职」）。仍不行的话，单独跑一次采集自测，可以直接看到请求与解析过程：

```bash
python -m spiders.xmu_career
```

**Q：筛选结果是 0 条**
先执行 `python main.py --stats`，看库里实际有哪些数据，再放宽条件：调低 `--min-score`、去掉 `--city`，或换用更宽的 `--level`。

**Q：想清空重来，或库里混进了不需要的岗位**
用 `--reset-db` 在下次取数前清空数据库：`python main.py --reset-db --city 厦门`。

**Q：第二次运行为什么这么快？会不会漏掉数据？**
第二次及以后默认走增量：列表页照常全量翻，但详情页只抓「新出现的 / 列表信息有变的 / 从没抓到过专业的 / 超过 7 天没刷新的」岗位，其余用 ODS 里的历史快照回填。跳过的是**重复请求**，不是数据——专业要求、截止时间都会从历史快照补回来，不会被抹空。想强制全部重抓加 `--full-refresh`。

**Q：怎么知道某个岗位的薪资改过？**
`python main.py --ods-changes 30` 列出最近 30 天所有发生变化的位置；`python main.py --ods-history <职位ID>` 看单个岗位的完整轨迹（哪一次抓取、当时是什么值、哪一次开始变的）。职位 ID 就是原文链接 `/job/view/id/` 后面那串数字。

**Q：改了 `config.py` 的权重表，但分数没变**
已有记录的分数不会自动更新。执行 `python main.py --rescore`，按新规则重算库里全部岗位（不联网）。

**Q：为什么很多岗位是 B 级或 C 级？**
等级是分层池子，不是合格线：S≥25 重点看，A≥16 值得投，B≥8 可以扫一眼，C 基本不对口。库里绝大多数岗位来自整个厦门招聘市场（教师、销售、行政、制造等），它们落在 C 级是正常的——**筛不出对口岗位才是问题，C 级多不是**。

**Q：有些岗位没有薪资或专业要求**
站点本身没有提供该字段。程序的原则是**保留而不是剔除**——信息缺失不等于不满足条件，宁可多给你看一条。若某条岗位的专业字段确实取不到，会标注「专业字段缺失」，不会被当成「不匹配」。

**Q：取一次数据要多久？会不会给站点造成压力？**
默认口径（约 30 条）约 1 分钟；放开专业取全量（约 300 条）约 8-10 分钟，主要时间花在逐条补「需求专业」上。程序对每次请求都做了 ≥1.5 秒的节流，并且只抓公开页面、不登录、不绕过任何访问控制。

**Q：能用在别的城市或别的学校吗？**
城市可以直接换——从 `CITY_CODES` 里挑一个填到 `--search-city` 即可。换到其他学校的就业网站，则需要另写一个对应的采集模块。

## 版本历史

版本号取自 `config.py` 的 `VERSION`（唯一来源），编号规则是[语义化版本](https://semver.org/lang/zh-CN/)：
**不兼容改动进 MAJOR，新增功能且向后兼容进 MINOR，只修 bug 进 PATCH。**

### v1.4.0 — 2026-09-24 · DWD 清洗层与技能标签

规划里「最有含金量」的一步：原始文本能存不能用，这一版把它们变成可聚合的列，并给每个岗位打上技能标签。顺带发现并堵上了一个下架判定的漏洞。

| 变更 | 说明 |
|---|---|
| DWD 明细层 | 新增 `dwd_job_detail`：薪资拆月薪区间、城市拆省市三级、学历归一成枚举、经验映射成年限区间 |
| 技能标签 | 新增 `dwd_job_skill`：从岗位名 / 需求专业 / 职能类别 / 语言要求抽词，别名归一，短英文别名加词边界防误伤 |
| 技能词典 | 新增 `config.SKILL_DICT`：57 个技能条目、四类别（技术栈 / 业务领域 / 外语 / 通用能力） |
| 新增详情字段 | 解析并采集工作经验 / 职能类别 / 语言要求 / 招聘人数 / 完整工作地点五项 |
| 新增命令 | `--build-dwd` 从 ODS 重算清洗层（不联网、秒级、可反复重跑）、`--dwd-stats` 看质量与技能榜 |
| 增量适配 | 新增 `detail_schema_version`：解析器学会新字段时版本号 +1，老快照据此自动排进重抓队列，抓完一轮即收敛 |
| **下架判定加固** | 判定「列表里没出现 = 已下架」原来只看「时间范围不限 + 翻页未触顶」两条前提。本次补上第三条：**本批检索口径必须与上一批一致**。口径一变窄，结果数骤降，"没出现"根本不成立 |

关于最后一条：实测用默认的三专业口径跑了一次，列表从 294 条掉到 24 条，270 个岗位被判为「未再出现」，其中 266 条真被标成了下架，而全程没有任何报错——因为前两条前提都成立。现在口径不一致时会**只记录不判定**，并在日志里写明两侧口径。

自动化测试从 194 个增加到 **332 个**，全部通过（新增 DWD 清洗与技能抽取 96 个、增量规则 4b 与回填 13 个、检索口径与下架闸门 29 个）。
